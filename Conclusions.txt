For this program, we started with an existing Pacman game from GitHub and modified it so that each ghost uses a different algorithm to decide how to move. The original game mostly used simple or random movement, but we changed it so that each ghost follows a specific approach based on the algorithms discussed in the paper and in class. The goal was to actually implement those algorithms into ghost movements in the code and see how it changes gameplay.
The game board is like a grid-based graph, where each tile is a node and each possible movement (up, down, left, right) is an edge. In our code, each ghost recalculates its path/direction whenever it reaches a tile, then moves one tile in that direction. This makes the movement smoother and prevents the ghosts from possibly changing direction in the middle of a tile.

Instead of rewriting the whole game, we modified the ghost behavior inside the existing structure. Specifically, we updated the moveGhosts method so each ghost calls a different movement method (moveBlinky, movePinky, moveInky, and moveClyde). Inside those methods, we added our own pathfinding logic. 
We also added checks like isAtTile and isAtIntersection so ghosts only recalculate their path at decision points instead of constantly changing direction, which made the movement smoother and more realistic.

Blinky uses a breadth-first search (BFS) algorithm to chase Pacman directly. In the code, we implemented BFS using a queue, a set, and a parent map to reconstruct the path. BFS goes through the grid level by level until it finds Pacman, and then we follow the path back to the ghost to get the first direction it should move. 
This ensures the shortest path in terms of number of moves, so Blinky is very reliable. However, because it only targets Pacman’s current position and does not consider future movement that Pacman takes while it moves through the path, Blinky can feel easier to avoid and like it is always one step behind Pacman. 

Pinky uses the A* algorithm, which we implemented using a priority queue and an AStarNode class to track the cost values (g, h, and f). We used Manhattan distance as the heuristic. Based on the paper, Pinky does not target Pacman’s current tile, but instead targets a tile a few steps ahead based on Pacman’s direction. This makes Pinky feel more aggressive because it tries to cut Pacman off instead of following behind like Blinky. 
In gameplay, this made Pinky seem more effective at chasing than Blinky, especially when Pacman is moving in a straight direction.

For Inky, we implemented a hybrid approach that switches between direct chasing and predictive targeting. 
In the code, Inky first checks its Manhattan distance from Pacman. If Inky is close to Pacman, it usually uses BFS to chase Pacman directly, so it behaves more like Blinky. 
However, there is still a small random chance that it uses the predictive method (20%) so it does not get stuck doing the same direct following chase every time. 
If Inky is farther away, it uses a more predictive A* approach. The getInkyTarget method looks ahead to Pacman’s next intersection, chooses a possible direction from that intersection, follows that direction to another intersection, and uses that point as Inky’s target. 
Then aStarDirectionToTarget finds a path to that predicted target. This makes Inky harder to predict because it sometimes chases directly and sometimes tries to cut off where Pacman may be going instead of following like some of the other ghosts.

Clyde uses the simplest behavior. It mostly relies on the basic movement logic originally implemented in the Pacman game and does not use a path finding algorithm. This makes Clyde the least consistent and aggressive ghost in terms of efficiency, but it also adds good variation to the gameplay since its movement is not always optimal like the other three ghosts, which always feel like they are closely chasing you. 

Overall, this project showed us how different algorithmic approaches affect the gameplay of a previously simple game. Certain algorithms thrive in certain situation or with certain game “maps”, and playing this version of Pacman shows that. 
For example, BFS works very well when the goal is just to find the shortest path, but in a game setting it can feel less effective because it does not account for movement during the path traversal or prediction. 
A* performs better in many cases because it uses a heuristic and a smarter target, which allows it to react better to how Pacman is moving. However, even A* is not always perfect, especially in tighter parts of the maze where predicting too far ahead can lead to less optimal movement.
The hybrid approach for Inky shows that combining strategies can create more interesting and less predictable behavior without needing very complicated code (we were able to reuse a lot of our existing code). By mixing direct chasing and prediction, Inky can perform better than either approach alone depending on the situation. 

One limitation is that all of the algorithms are recomputed at intersections, which works fine for this small grid but would likely be inefficient for larger maps or more complex games. 
Also, while BFS guarantees optimal paths and A* improves efficiency with heuristics, both approaches still depend on how the problem is structured, so no one algorithm is always the best in every situation. 

When to use what:
BFS seemed better when the ghost was already close to Pacman because it gives the shortest direct path to Pacman’s current tile without needing extra prediction. 
A* seemed better when the ghost was farther away or when trying to cut Pacman off, because the heuristic and predicted target help guide the ghost toward where Pacman is likely going. 
For Inky, we hybridized these by making it switch between the two ideas: when Inky is close, it usually uses BFS to chase directly, and when it is farther away, it uses A* toward a predicted future intersection. Our reasoning was that direct chasing is useful when Pacman is nearby, but prediction is more useful when there is enough distance for Pacman to change position. 
The hybrid approach is not always more efficient than BFS or A* by itself, but it can be more effective in gameplay because it adapts to th situation instead of always using the same strategy like the other two.

One thing we learned from this project is how the different algorithm types we studied in class actually behave in a real application, especially something cool like a game of Pacman. BFS is a straightforward graph traversal that guarantees the shortest path, but it does not take advantage of any additional information. 
A* improves on this by using a heuristic, which is something we talked about when discussing algorithm efficiency and design. This made it more practical in a game setting where predicting movement matters because Pacman is not staying still while the ghosts are chasing. 
The hybrid approach also helped show that sometimes combining ideas from different algorithms can create better behavior without needing to design a completely new algorithm. Overall, this project made the differences between graph traversal, heuristic search, and algorithm design more clear than just learning them in class and through visualizations.
